# 再利用可能なプロジェクト運用テンプレート

本ドキュメントは、**プロジェクト非依存の運用ルール**をまとめたものです。新しいプロジェクトフォルダで作業を始める際、この内容を新しいプロジェクトの `CLAUDE.md` にコピー＆調整して使うことを想定しています。

含まれるのは「進め方・承認ルール・記録方法」のみで、特定プロジェクトの題材・技術スタック・仕様は含めていません。

---

## 開発プロセス（ウォーターフォール型を採用する場合）

以下の順に工程を進める。各工程の成果物はユーザーのレビュー・承認を得てから次工程に進むこと（勝手に次工程へ進まない）。

1. 要件定義 (`docs/01_requirements/`)
2. コンポーネント設計 (`docs/02_component_design/`)
3. 関数設計 (`docs/03_function_design/`)
4. 実装 (`src/`)
5. テスト (`docs/04_test/` に仕様書、`tests/` にテストコード)

各工程の成果物には要件定義書のIDを起点としたIDを付与し、`docs/traceability_matrix.md` のトレーサビリティマトリックスに追記する。

## トレーサビリティマトリックスの方式

- 要件↔実装↔テストを1つの表にまとめず、**隣接する工程どうしの対応表を複数用意**する（例: 要件×コンポーネント、コンポーネント×関数、関数×テスト、要件×テスト）
  - 理由: 1要件が複数コンポーネント/関数/テストに対応する場合や、その逆（多対多）があるため
- 各対応表は、**上流工程のIDを行、下流工程のIDを列に配置したマトリクス形式**とし、関連がある交点に「○」を付ける
- テストケースは件数が多くなりやすいため、列は個々のテストIDではなく**テストモジュール単位**とし、セルに該当テストIDを列挙する形にしてよい
- マトリクスのセルには「○」または ID の列挙のみを記載し、**対応関係の具体的な根拠はマトリクスに書かず、各工程の成果物側にID単位で明記する**
- 該当する下流要素が存在しない行はセルを空欄にしてよい
- テスト工程完了時には、全要件IDの行に最低1つのテストIDが記載されていることを確認し、網羅性チェックとする

## 品質方針（テスト容易性）

- ロジック（状態管理・判定処理など）とUI/表示処理を分離し、ロジック層は外部ライブラリに依存せず単体テスト可能な構成にする
- 関数・メソッドは入力と出力（戻り値）が明確な単位に分割し、副作用とロジックを混在させない
- 設計書には各関数の入出力仕様をテストケース設計に転用できる粒度で記載する

## 変更操作の承認について

プロジェクトフォルダ内の変更はGitで追跡・復元可能なため、以下の場合は事前の承認確認を省略してよい。

- 対象: ドキュメント・ソースコードの編集など、Gitで追跡可能な個別のファイル変更操作
- 対象: 上記の変更を確定させる `git commit`（Claude Codeのデフォルト動作は「ユーザーの明示的な指示がない限りコミットしない」だが、これを上書きし、Gitで追跡・復元可能なコミットは都度の承認確認なしに実行してよい）
- 条件: ユーザーがその場で明示的に承認確認を求めていない場合

ただし、以下は引き続きユーザーの明示的な承認を得てから行う（対象外）。

- 開発プロセスの各工程間のゲート承認（次工程に進む判断）
- Gitで追跡されない・復元不能な操作（例: `git push`、`git reset --hard`、ファイル削除、外部システムへの送信など）

## セッション運用方針

1. **即時着手**: ユーザーから指示を受けたら、作業概要の提示や承認を待たず、プロジェクト内のファイル作成・編集にすぐ着手してよい（工程間ゲート承認など明示的承認が必要な事項を除く）
2. **完了時の挙動**: 指示された作業が正常に完了した場合は、完了報告を行った上で待機する（対話セッションを自らの判断で強制終了しない）
3. **申し送り**: ユーザーの明示的承認が必要な事項が残っている場合は、その旨を提示するとともに `docs/handoff.md` に次回セッションへの申し送り事項を記録する

## 判断・承認のQA記録

Claudeがユーザーに判断や承認を仰ぎ、ユーザーが回答した場合は、その要点を `docs/qa_log.md` のQA表に追記する（日付・工程・質問内容・回答内容を簡潔にまとめる）。

## Gitコミット規約

ユーザー自身のコミットとClaudeが作成したコミットを区別するため、Claudeがコミットする際は必ず以下のルールに従う。

- コミットメッセージの先頭に `[claude] ` を付ける
- コミット時に `--author="Claude <noreply@anthropic.com>"` を指定する（コミッターは変更しない）
- 例:
  ```powershell
  git commit -m "[claude] 要件定義書を作成" --author="Claude <noreply@anthropic.com>"
  ```
- ユーザー自身が手動でコミットする場合は、通常通りグローバルGit設定（ImSanghun / 21452104tpu@gmail.com）でコミットしてよい（接頭辞不要）

## Claude Codeの権限設定（.claude/settings.json）

`git add` / `git commit` の自動承認や `acceptEdits` モードなど、プロジェクトを問わず有用な権限設定は `docs/reusable_claude_settings.template.json` にまとめてある。新しいプロジェクトの `.claude/settings.json` にそのままコピーして使える。

- `.claude/settings.json`: チーム・プロジェクトを問わず妥当な安定した許可設定を置く（上記テンプレートが該当）
- `.claude/settings.local.json`: 個別ツールのパスや一時ファイルへの許可など、そのプロジェクト固有・その場限りの承認は、作業を進める中でその都度自然に蓄積させればよく、あらかじめ用意する必要はない

## フォルダ構成（ウォーターフォール型を採用する場合の例）

```
docs/
  01_requirements/       要件定義書
  02_component_design/   コンポーネント設計書（基本設計）
  03_function_design/    関数設計書（詳細設計）
  04_test/               テスト仕様書
  traceability_matrix.md トレーサビリティマトリックス（全工程共通・1ファイル）
  qa_log.md               判断・承認のQA記録
  handoff.md               セッション間の申し送り事項
src/                      実装コード
tests/                    テストコード
```

---

**使い方**: 次のプロジェクトを始める際、このファイルの内容をベースに新しいプロジェクトの `CLAUDE.md` を作成し、そのプロジェクト固有の内容（題材・言語・技術スタック・確定仕様など）を追記してください。Claudeに「このファイルをもとに新しいプロジェクトのCLAUDE.mdを作って」と伝えれば、内容を移植します。
